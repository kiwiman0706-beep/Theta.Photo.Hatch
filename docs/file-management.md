# Theta.Photo.Hatch — ファイル管理構想（Draft v0.1 / 2026-10-29）

## 0. 基本原則

1. **ファイルとメタデータの「正」は NAS 上のファイルそのもの**
   - アプリの DB は「キャッシュ（索引）」に過ぎない。消えても NAS をスキャンすれば完全に再構築できること。
2. **メタデータは業界標準（XMP / IPTC）で書く**
   - ☆・キーワード・イベント名を独自 DB や Synology Photos の DB だけに持たない。
   - Hatch が無くなっても、ExifTool / digiKam / Lightroom などで読めることを合格ラインとする。
3. **原本（オリジナル）は書き換えない**
   - メタデータは XMP サイドカー（`.xmp`）に書く。ハッシュが変わらないのでバックアップ差分・重複判定が安定し、HEIC/MP4 でも安全。
4. **フォルダは「1軸」だけ。それ以外はすべてメタデータ**
   - 物理的な置き場所で表現するのは「公開範囲（＝アクセス権）」と「年/イベント」だけ。
   - ☆・キーワード・共有済み先 などは全部 XMP。
5. **外部サービス（Amazon フォト / みてね）は「出力先」であって保管場所ではない**
   - コピー用フォルダを常設せず、「どこに送ったか」を記録して二重送信を防ぐ。

## 1. 状態モデル：未処理 = Inbox にある

処理状態を DB ではなく **場所** で表現する。これが一番整合性が崩れにくい。

```
撮影 ─▶ スマホ ─(自動バックアップ)─▶ NAS: Inbox/        ← 未処理（Hatch の一覧に出る）
GoPro ─(取り込み)────────────────────▶ NAS: Inbox/
                                         │  Hatch で選択して「処理」
                                         ▼
                        Library/<公開範囲>/<年>/<イベント or 年月>/   ← 処理済み（一覧から消える）
                        Trash/                                        ← 不要（30日後に削除）
```

- Inbox が空 ＝ 処理完了。UI の「全部消えたら完了」と 1:1 で一致する。
- 処理 = 「移動 + リネーム + XMP 作成」を 1 トランザクションとして扱う（後述のジャーナル）。

## 2. フォルダ構成（案）

```
/volume1/homes/<user>/Photos/              ← 個人スペース（自分だけ）
  Inbox/
    MobileBackup/<端末名>/                  ← Synology Photos アプリの自動バックアップ先
    GoPro/<取り込み日>/
  Private/                                  ← 見返したくない記録（事故の傷・書類等）
    2026/2026-10-29_車の傷/
  Memo/                                     ← メモ写真（ホワイトボード・値札・駐車位置…）
    2026/2026-10/
  Trash/

/volume1/photo/                             ← 共有スペース（家族も見る）
  Family/
    2026/
      2026-10-29_布引ハーブ園/
        20261029_103512_IMG_1234.HEIC
        20261029_103512_IMG_1234.MOV        ← Live Photo の動画側（同じ basename）
        20261029_103512_IMG_1234.xmp        ← サイドカー（1アセット1ファイル）
      2026-10/                              ← イベントに属さない日常写真
```

### なぜ最上位を「公開範囲」で分けるか
- Synology のアクセス権・個人/共有スペースはフォルダ単位。事故写真のような物は
  **アクセス権で物理的に隔離** するのが一番安全（タグだと設定ミスで漏れる）。

### イベントフォルダ名
- 推奨：`2026-10-29_布引ハーブ園`（または `20261029_布引ハーブ園`）
- `|`（半角）は Windows で使用不可。全角 `｜` は使えるが、
  コマンドライン操作・URL・他OSで扱いにくいので `_` を推奨。
- 複数日イベント：`2026-08-10~12_北海道旅行` のように開始日で並ぶ形に。
- **Unicode 正規化は NFC に統一**（macOS は「ブ」を NFD で書くことがあり、同名なのに別フォルダ化する事故が起きる）。

### ファイル名
- `YYYYMMDD_HHMMSS_<元ファイル名>.<拡張子>` にリネーム
  - GoPro の `GOPR0001.JPG` や iPhone の `IMG_0001.HEIC` は番号が一周して衝突するため。
  - 時刻で並ぶので、どのツールで見ても時系列になる。
  - 元ファイル名を残すので逆引きできる。XMP の `xmpMM:PreservedFileName` にも保存。
- 時刻は EXIF `DateTimeOriginal` + `OffsetTimeOriginal`（ローカル時刻）。無い場合は動画の作成日時 → ファイル更新日時の順でフォールバック。
- **GoPro は時計ズレ・タイムゾーン無し** が多いので、取り込み時に「時刻補正（+N 分）」機能を用意。

## 3. メタデータ（XMP）マッピング

| Hatch の概念 | XMP プロパティ | 備考 |
|---|---|---|
| ☆（大事） | `xmp:Rating` (0–5) | ☆1個で運用するなら 5 を立てる。ほぼ全ツール対応 |
| キーワード | `dc:subject` | 階層化するなら `lr:hierarchicalSubject`（`人物|長男` 等）も併記 |
| イベント名 | `Iptc4xmpExt:Event` | フォルダ名と二重持ちだが、ファイル単体で持ち出しても失われない |
| 場所名 | `Iptc4xmpCore:Location` / `photoshop:City` | 任意 |
| 元ファイル名 | `xmpMM:PreservedFileName` | リネーム前の名前 |
| カテゴリ | `xmp:Label` もしくはフォルダで表現 | Family / Memo / Private |
| 共有履歴 | `hatch:SharedTo`（独自名前空間） | 例 `amazon-photos@2026-10-29`, `mitene@2026-10-29` |
| 処理日時 | `hatch:ProcessedAt`（独自名前空間） | |

- 独自名前空間 `hatch:`（例 `http://ns.theta-photo-hatch/1.0/`）は「標準に無いものだけ」に限定する。
- サイドカーの命名は `<basename>.xmp`（Adobe 形式）。Live Photo の HEIC+MOV、GoPro の GPR+JPG のような
  **ペアは 1 アセット = 1 XMP** で共有できる。

## 4. 外部サービス連携

| 出力先 | 公式 API | 方針 |
|---|---|---|
| Amazon フォト | 一般向けの公開 API なし（Amazon Drive API は終了） | スマホの共有シート経由で Amazon フォトアプリへ渡す。**スマホ側の Amazon フォト自動アップロードは OFF**（Echo に全部出る原因）。Echo Show 側も特定アルバムだけ表示に設定 |
| みてね | 公開 API なし | 共有シート経由でみてねアプリへ渡す |
| Synology Photos | **非公式** Web API（`SYNO.Foto.*` / 共有スペースは `SYNO.FotoTeam.*`）。仕様変更リスクあり | 表示用ビューとして扱い、XMP → Synology のタグ/アルバムへ **一方向ミラー**（任意機能） |
| Synology File Station | **公式** API（`SYNO.FileStation.*`：一覧・移動・リネーム・アップロード・サムネイル） | NAS 上のファイル操作はこちらを使う |

- 送信したら `hatch:SharedTo` に記録 → 二重送信防止、「みてね未送信の家族写真」などの抽出が可能。
- 送信時オプション：位置情報（GPS）を削除してから渡す。

## 5. システム構成（案）

```
[スマホ: Hatch (Flutter)]  ── HTTPS (Tailscale / QuickConnect) ──▶  [NAS: Hatch Server (Docker)]
   ・Inbox 一覧（時系列/日付単位選択）                               ・Python + ExifTool + SQLite(キャッシュ)
   ・分類/イベント/☆/キーワード入力                                 ・移動・リネーム・XMP書き込み
   ・共有シートで Amazon/みてね へ                                   ・File Station / Synology Photos API 連携
```

- 重い処理（ExifTool による XMP 書き込み、ハッシュ計算、索引）は NAS 側。スマホはサムネを見て選ぶだけ。
- MVP ではサーバ無しで、スマホから File Station API を直接叩く構成も可能（XMP 生成は Dart で）。

## 6. 整合性を保つための仕組み

- **操作ジャーナル**：処理は `journal/YYYYMMDD.jsonl` に「移動元→移動先・作成した XMP」を追記してから実行。
  途中で落ちても再実行・取り消し（Undo）ができる。
- **重複検出**：SHA-256 をキャッシュ DB に保持。スマホ経由と GoPro 直接取り込みの二重登録を検知。
- **アセットグループ**：Live Photo（HEIC+MOV）、GoPro（JPG+GPR、MP4+LRV+THM）、連写などは必ず一緒に動かす。
  LRV/THM はプレビュー用なので Trash 行きでよい。
- **再構築テスト**：キャッシュ DB を消して NAS を再スキャン → 同じ状態に戻ることを定期的に確認（ロックインしていない証明）。
